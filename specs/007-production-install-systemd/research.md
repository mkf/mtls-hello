# Research: Production Install & Systemd Service

**Feature**: 007-production-install-systemd | **Date**: 2026-08-05

## Decision: Random port via pre-bind

**Decision**: When `--port=0` is given, the server pre-binds a temporary TCP socket to port 0, reads the OS-assigned port, closes the socket, then passes the assigned port to vibe.d's `listenHTTP`.

**Rationale**:
- vibe.d's `HTTPServerSettings` accepts a concrete port number. Listening on port 0 and then extracting the assigned port requires platform-specific introspection of vibe.d's internal listener, which is fragile.
- Pre-binding is the standard portable pattern: request an ephemeral port from the kernel, get the assigned port, then use it explicitly. The race window between close and re-bind is negligible (the kernel cycles ephemeral ports from a wide range).
- The D standard library's `std.socket.Socket` or `TcpSocket` provides `bind` with port 0, then `sock.localAddress().port()` gives the assigned port.

**Alternatives considered**:
- `listenHTTP` with port 0 and inspect `listener.bindAddresses` afterwards — requires vibe.d's TCP listener to expose the actual bound address, which depends on implementation details. Rejected as fragile.
- systemd socket activation — the server would inherit a pre-bound socket from systemd. Overkill for a user service; the operator would need to configure a socket unit. Rejected for simplicity.

## Decision: Port file written atomically

**Decision**: The port file is written by creating a temp file in the same directory, writing the port number to it, then `rename(2)`-ing it into place.

**Rationale**:
- `rename` is atomic on Linux when source and destination are on the same filesystem. Observers (systemd, scripts) see either the old file or the complete new file, never a partial write.
- Using a temp-file + rename pattern avoids the need for file locking or signaling.
- The port file contains just the port number (no newline, no prefix) for easy machine consumption: `cat $PORT_FILE` yields the raw port number.

**Alternatives considered**:
- Write port to stdout for systemd capture — systemd captures stdout to the journal, but parsing a port number from journald requires `journalctl -o json` plumbing. A port file is simpler for `ExecStartPost` scripts.
- Include `PORT=` prefix — adds parsing burden in shell scripts. Plain number is trivially consumable via `$(cat file)`.

## Decision: `--version` flag prints dub.json version

**Decision**: The server reads its version string from a compile-time constant embedded during the build. The `dub.json` version field is the source of truth.

**Rationale**:
- The project already uses dub, which has a `version` field in `dub.json`.
- At build time, a `string version = "..."` constant can be injected via D's `-version=` compiler flag or by reading from a generated module.
- For `dub build`, the version can be written to a D source file as a string literal during the pre-build step, or the build script can write a `version_.d` file with the version constant.

**Alternatives considered**:
- Parse `dub.json` at runtime — requires shipping the JSON file with the installed binary. Rejected (brittle, requires JSON parsing).
- Hardcode version in `source/app.d` — duplicates the version; inconsistency risk. Rejected.
- Use git describe — useful but requires git at build time. The dub.json version is simpler.

## Decision: `just install` copies binary and handlers via shell script

**Decision**: `just install` delegates to a new `scripts/install.sh` that:
1. Ensures `~/.local/bin/` exists (mkdir -p)
2. Copies `mtls-hello` to `~/.local/bin/mtls-hello` with `install -D -m 755`
3. Copies `handlers/` to `~/.local/share/mtls-hello/handlers/` with `cp -r`

**Rationale**:
- `install -D` handles directory creation and permission setting in one command.
- `~/.local/bin` follows the XDG Base Directory specification (`$XDG_BIN_HOME` default).
- `~/.local/share` is the standard data directory (`$XDG_DATA_HOME` default).
- Using a shell script keeps the justfile clean and allows standalone invocation (`bash scripts/install.sh` without `just`).

**Alternatives considered**:
- Use dub's built-in install — dub doesn't have a standard install target. Rejected.
- Single all-in-one script — mixing install and service generation in one script couples them unnecessarily. Two scripts is cleaner.
- Install to `/usr/local` — requires root; violates the "for my user" constraint. Rejected.

## Decision: systemd user service unit generated by shell script

**Decision**: `scripts/install-service.sh` generates a unit file using `cat` with a heredoc template, writing to `~/.config/systemd/user/mtls-hello.service`.

The unit file template:

```ini
[Unit]
Description=mtls-hello mutual-TLS server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=%h/.local/bin/mtls-hello --port=0 --port-file=%t/mtls-hello.port --no-multicast --handlers-dir=%h/.local/share/mtls-hello/handlers [cert] [key]
ExecStartPost=/bin/sh -c 'echo "mtls-hello listening on port $(cat %t/mtls-hello.port)"'
Restart=on-failure
RestartSec=5s
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=default.target
```

**Rationale**:
- `%h` expands to the user's home directory; `%t` to the runtime directory (`/run/user/<UID>`).
- `Type=simple` is correct for a foreground server process.
- `Restart=on-failure` matches the spec: restart on crash, not on clean exit.
- `RestartSec=5s` prevents thrashing.
- Certificate and key paths are left as placeholders — the operator must supply them via a drop-in override (`systemctl --user edit mtls-hello`).
- The service uses `--port=0` for automatic port assignment and `--port-file` for port-file output.
- `--no-multicast` is sensible for a single-instance service (multicast is for peer discovery between LAN instances).
- The `ExecStartPost` line prints the port to the journal for operator convenience.

**Alternatives considered**:
- Generate the unit from a `.in` template with `sed` substitution — overkill; the template is small and has only a few placeholders.
- Use `systemctl --user edit --full` for template — requires interactive input. Rejected.
- Embed certificate paths in the template — certificates are deployment-specific; the operator should provide them via a drop-in. Rejected.
- Socket activation — adds complexity (socket unit, Accept=no) with no clear benefit for a single-instance service. Rejected.

## Decision: BATS tests for install and service generation

**Decision**: Tests verify:
1. `just install` creates correct files at correct paths with correct permissions
2. `just install` is idempotent (running twice doesn't fail)
3. `just install-service` creates a valid service file
4. `just install-service` refuses to run without a prior install
5. `systemd-analyze verify` passes on the generated unit (if systemd-analyze is available)
6. `--port=0` picks a random port and writes the port file
7. `--version` prints a non-empty version string

BATS tests use a temporary `HOME` to avoid polluting the real home directory.

**Rationale**: All user stories have clear, independently testable acceptance criteria. BATS already handles TLS-server testing in this project.
